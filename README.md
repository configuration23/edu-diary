# edu-diary

Электронный дневник колледжа: журнал, посещаемость, домашние задания, аналитика и связь с
родителями.

Проектная документация — в [docs/README.md](docs/README.md), порядок работ — в
[docs/ROADMAP.md](docs/ROADMAP.md).

**Текущее состояние: Этапы 0–1.** Есть фундамент (монорепозиторий, стек в Docker, миграции,
тесты, проверки в CI) и основа работы: мастер первого запуска, вход с ролями и правами,
пользователи, аудит изменений и доступа, события безопасности, согласия и политика обработки
ПДн. Журнала, оценок и домашних заданий ещё нет — это Этапы 3–5.

Учётных записей «из коробки» не существует: первый администратор создаётся мастером настройки
при первом открытии приложения.

## Что уже работает

- Монорепозиторий на npm workspaces: `apps/api`, `apps/web`, `packages/contracts`, `packages/domain`.
- `docker compose` поднимает `postgres`, `migrate`, `api`, `web`, `caddy`.
- Миграции Drizzle Kit и команда `npm run migrate` (отдельным шагом, не при старте API).
- Каркас Fastify: `/api/health` (процесс, БД, состояние миграций), единый формат ошибок,
  структурированные логи с `requestId`.
- Мастер первого запуска: заведение и брендинг, учебный год и период, администратор, хранилище.
  До его прохождения все API, кроме `/api/health` и `/api/setup/*`, отвечают `503 SETUP_REQUIRED`.
- Вход по логину и паролю (argon2id), серверные сессии в cookie, блокировка после серии неудачных
  попыток, смена пароля со сменой всех остальных сессий.
- Роли и права со областью действия (`own`/`group`/`assigned`/`all`), управление пользователями.
- Аудит: изменения и доступ к персональным данным, журнал только на добавление.
- События безопасности: всплеск неудачных входов, блокировка учётной записи, изменение прав,
  доступ вне области действия; разбор события в админке.
- Согласия законных представителей и редакции политики обработки ПДн, список учеников без согласия.
- Vitest и Playwright; тесты архитектуры, сборки и секретов.
- CI: проверки, тесты, сквозные сценарии и фактический запуск стека в `docker compose`.

## Требования

- Node.js 22 и npm 10 (см. `.nvmrc`).
- Docker с поддержкой Compose v2 — для запуска стека и для локальной базы.

## Быстрый старт: весь стек в Docker

```bash
npm run bootstrap:env    # создаёт .env со случайными секретами
docker compose up        # собирает образы и поднимает стек
```

- Приложение: <http://localhost:8080>
- Состояние системы: <http://localhost:8080/api/health>

Остановить: `docker compose down`. Удалить данные: `docker compose down -v`.

По умолчанию `SITE_ADDRESS=:8080` — это «любой хост на порту 8080», поэтому стенд открывается и
по IP, и по имени машины: `http://192.168.1.70:8080`. Если порт 8080 занят, задайте в `.env`
другой `HTTP_PORT` — и тот же порт в `SITE_ADDRESS`. Для домена с HTTPS укажите
`SITE_ADDRESS=diary.example.ru` и запускайте с `-f docker-compose.prod.yml`.

`npm run bootstrap:env` обязателен: секретов в репозитории нет, и приложение намеренно не
стартует, если `DATABASE_URL`, `SESSION_SECRET` или `STORAGE_ENCRYPTION_KEY` не заданы или
равны примерам из `.env.example` ([docs/SECURITY.md](docs/SECURITY.md) §3.2).

## Первый запуск: мастер настройки

На пустой базе приложение не пускает никуда, кроме мастера: так требование «учётных записей
по умолчанию нет» выполняется технически, а не на словах (ADR-014).

1. Откройте приложение. Мастер покажет проверку окружения: доступность базы и состояние миграций.
   Если миграции не применены — выполните `npm run migrate` и обновите страницу.
2. Шаг «Учебное заведение»: название, короткое имя, подпись, логотип (PNG/JPEG/SVG до 256 КБ).
3. Шаг «Учебный год и период»: год и первый период (семестр, четверть или триместр).
4. Шаг «Администратор»: логин, ФИО и пароль. Требования к паролю — минимум 10 символов, не
   совпадает с логином и не входит в список распространённых.
5. После завершения администратор входит автоматически, мастер закрывается навсегда.

Дальше: раздел «Пользователи и роли» — завести преподавателей, учеников и родителей; «Согласия
и политика» — опубликовать редакцию политики обработки ПДн, добавить учеников, привязать
законных представителей и зафиксировать согласия; «Аудит» и «Безопасность» — смотреть, кто что
делал и что требовало внимания.

## Роли и права

Роли «из коробки»: `admin`, `teacher`, `student`, `parent`. Каталог прав и наборы прав системных
ролей лежат в коде (`apps/api/src/modules/iam/iam.catalog.ts`) и синхронизируются при старте:
новые права добавляются, уже изменённые администратором наборы не перезаписываются.

Право — строка `resource:action` (`users:read`, `grades:write`, …), область действия —
`own` ⊂ `group` ⊂ `assigned` ⊂ `all`. Область `own` для родителя означает «свои дети»: конкретные
ученики определяются привязками и проверяются в сервисах (ADR-005), а не настройками.

Инварианты, которые нельзя снять настройками: ученик видит только свои данные, родитель — только
своих детей, учитель — только свои назначения; записи аудита и согласий недоступны для изменения
или удаления через API. Каждый инвариант покрыт тестом.

## Разработка без контейнеров

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d postgres   # база на 127.0.0.1:5432
npm install
npm run bootstrap:env
npm run migrate
npm run dev          # API на http://127.0.0.1:3000
npm run dev:web      # интерфейс на http://127.0.0.1:5173 (проксирует /api на API)
```

Если 5432 занят, задайте в `.env` другой `POSTGRES_PORT` и тот же порт в `DATABASE_URL`
и `TEST_DATABASE_URL`. Отдельная база `edu_diary_test` для интеграционных тестов создаётся
автоматически при первом запуске контейнера (`docker/postgres-dev-init.sql`).

## Структура

```
apps/api              Fastify: модульный монолит
  src/modules/*       модули (setup, auth, iam, academics, audit, security, privacy,
                      settings, health) со своим публичным входом index.ts
  src/shared/*        общая инфраструктура: env, логи, ошибки, БД, права, пароли
  drizzle/            SQL-миграции и журнал Drizzle
  test/               тесты API (unit + интеграционные с PostgreSQL)
apps/web              React 19 + Vite + Tailwind, TanStack Query и Router, React Hook Form
packages/contracts    Zod-схемы API, общие для сервера и клиента
packages/domain       чистая доменная логика: даты (ADR-016), политика паролей, права и scope
tools/                проверки качества и вспомогательные скрипты
e2e/                  сквозные сценарии Playwright
docs/                 проектная документация (VISION, ARCHITECTURE, SECURITY, DECISIONS, ROADMAP)
```

## Что проверяется машиной, а не «помним и не делаем»

| Правило                                                    | Где проверка                                                   |
| ---------------------------------------------------------- | -------------------------------------------------------------- |
| Модуль обращается к другому модулю только через `index.ts` | `tools/quality/architecture.mjs`, `npm run check:architecture` |
| SQL — только в репозиториях и схемах модуля                | там же                                                         |
| Пакеты не зависят от приложений и друг от друга            | там же                                                         |
| В клиентском бандле нет внешних доменов                    | `npm run build` (шаг `check-bundle-domains`)                   |
| В репозитории нет секретов                                 | `npm run check:secrets`, CI                                    |
| Приложение не стартует без секретов и при значении-примере | `npm run check:startup-secrets`, `apps/api/test/env.test.ts`   |
| Ученик, родитель и учитель не видят чужих данных           | `apps/api/test/permissions.test.ts`                            |
| Записи аудита и согласий нельзя изменить через API         | `apps/api/test/audit.test.ts`                                  |
| Сборка клиента идёт в production-режиме                    | `tools/quality/check-build-env.mjs` (шаг сборки клиента)       |
| Версии зависимостей зафиксированы                          | `package-lock.json`, `npm ci` в CI                             |
| Критические уязвимости зависимостей блокируют CI           | `npm audit --audit-level=high`                                 |

## Миграции

- Схемы Drizzle живут в модулях: `apps/api/src/modules/<модуль>/<имя>.schema.ts`.
- Новая миграция: изменить схему → `npm run db:generate` → проверить SQL в `apps/api/drizzle/`.
- Применение: `npm run migrate` (локально) или сервис `migrate` в compose. **Не** при старте API.
- Миграции только вперёд: откат делается новой миграцией ([docs/ROADMAP.md](docs/ROADMAP.md)).

## Переменные окружения

- Полный список с пояснениями — в [.env.example](.env.example).
- Обязательные секреты: `DATABASE_URL`, `SESSION_SECRET` (≥32 символа),
  `STORAGE_ENCRYPTION_KEY` (ровно 32 байта: base64 или 64 hex-символа).
- Файл `.env` подхватывается только при `NODE_ENV=development`. В production и test переменные
  задаёт окружение (docker compose, systemd, CI) — так «пустой» секрет не подставится из файла.
- Всё прикладное (брендинг, параметры правил) хранится в БД, а не в переменных окружения.

## Тесты

- `npm test` проходит на машине без базы: интеграционные тесты пропускаются без `TEST_DATABASE_URL`.
- С базой: `TEST_DATABASE_URL=... npm test` — каждый файл создаёт **свою** базу, применяет миграции
  и удаляет её после прогона: тесты Этапа 1 меняют состояние системы, и общая база делала бы
  результат зависимым от порядка запуска.
- Сборка клиента идёт **в production-режиме**: при `NODE_ENV=development` или `test` Vite
  подключает development-сборки зависимостей, и в бандл попадают адреса документации. Сборка
  останавливается на шаге `check-build-env` с понятным сообщением — запускайте `npm run build`
  без `NODE_ENV` или с `NODE_ENV=production`.
- Сквозные: `npm run build && npm run migrate && npm run test:e2e` (Playwright поднимет API и
  предпросмотр фронтенда сам). Сценарий Этапа 1 проходит мастер настройки, поэтому ему нужна
  **пустая** база: в CI она создаётся заново, локально её нужно пересоздать
  (`docker compose down -v` или отдельная база).

## Развёртывание

- Тестовый стенд и прод: `npm run bootstrap:env`, затем
  `docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d` с `SITE_ADDRESS=домен`
  — Caddy сам получит сертификат Let's Encrypt.
- Локально и на закрытом стенде стек отдаётся по HTTP на порту 8080 без сертификата.
- PostgreSQL наружу не публикуется; для разработки порт открывается только на `127.0.0.1`
  через `docker-compose.dev.yml`.
- Внешние образы (`postgres`, `caddy`, `nginx`) закреплены дайджестами: версия не меняется
  между сборками. `api` и `web` собираются из этого репозитория.
- Если у машины нет доступа к Docker Hub или она упирается в лимит анонимных скачиваний
  (`toomanyrequests`, `429 Too Many Requests`), укажите зеркало реестра в `.env`:
  `DOCKER_REGISTRY=mirror.example.ru/library/` — префикс подставляется к внешним образам.

### Секреты CI, влияющие на сборку

- `DOCKERHUB_USERNAME` и `DOCKERHUB_TOKEN` (Settings → Secrets and variables → Actions) —
  вход в Docker Hub на раннере. Без них скачивание образов идёт анонимно, а IP у
  GitHub-hosted раннеров общий: сборка периодически падает по лимиту реестра. Токен —
  access token Docker Hub с правом только на чтение. Если секреты не заданы, шаг входа
  пропускается и сборка работает как раньше.
