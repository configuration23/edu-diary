# ROADMAP — `edu-diary`

Принцип: каждый этап заканчивается **работающим приложением**, а не полуфабрикатом. Ничего не начинается, пока предыдущий этап не проходит свои критерии приёмки.

Тестовые данные создаются сидером (`npm run seed:demo`) только в dev/test. Продуктивная установка начинается с мастера настройки.

---

## Этап 0. Фундамент репозитория

**Состав**

- Монорепозиторий: `apps/api`, `apps/web`, `packages/contracts`, `packages/domain`.
- Docker Compose: `postgres`, `api`, `web`, `caddy` (локально — без HTTPS, на сервере — с автоматическим сертификатом).
- Миграции (Drizzle Kit) и команда `npm run migrate`.
- Каркас Fastify: `/api/health` (процесс + БД + состояние миграций), единый формат ошибок, структурированные логи с `requestId`.
- Vitest + Playwright настроены и запускаются в CI.
- Тест архитектуры: запрет импортов между модулями.
- Тест безопасности сборки: внешний домен в клиентском бандле роняет сборку (`SECURITY.md` §3.8).
- `npm audit` и проверка на утечку секретов в CI; фиксация версий lockfile.
- Проверка обязательных секретов при старте: приложение не поднимается без `DATABASE_URL`, `SESSION_SECRET`, `STORAGE_ENCRYPTION_KEY` и падает, если значение равно примеру из `.env.example`.
- Переменные окружения: `.env.example` с описанием, проверка обязательных на старте.
- Правила разработки, тестирования и развёртывания — `DEVELOPMENT.md`: порядок работы над
  шагом, требования к тестам и шлюзам, работа с миграциями, коммиты, деплой и откат. Правила
  растут из практики: каждый найденный грабль попадает в этот документ, а не остаётся в
  переписке.

**Критерии приёмки**

- `docker compose up` на чистой машине поднимает стек; `/api/health` отвечает `200` и показывает подключение к БД.
- `npm test` проходит; CI зелёный.
- Попытка импорта между модулями роняет сборку.
- Приложение отказывается стартовать без секретов и при значении-примере из `.env.example`.

## Этап 1. Мастер настройки, вход, пользователи и права

**Состав**

- Состояние «не настроено» → `503 SETUP_REQUIRED` на всех API, кроме `/api/setup/*`.
- Мастер: параметры БД → заведение (название, логотип, подпись) → учебный год и период → администратор → хранилище файлов.
- Хеширование паролей (argon2id), сессии в cookie, защита от перебора, смена пароля.
- Модуль `iam`: пользователи, роли, права и scope, привязка родитель↔ученик.
- Модуль `audit`: таблица и сервис, аудит входов, изменений пользователей/ролей и **доступа** к персональным данным (ADR-017).
- Согласия и политика: редакции политики обработки ПДн в БД, таблица `consent`, список учеников без согласия (ADR-021).
- Модуль `security`: журнал `security_event`, правила (всплеск неудачных входов, изменение прав), страница «Безопасность» в админке.
- Фронтенд: экран входа, мастер настройки, раздел «Пользователи и роли», раздел «Аудит» (базовый).

**Критерии приёмки**

- На пустой БД приложение не пускает никуда, кроме мастера; после его прохождения появляется рабочий вход.
- Учёток по умолчанию нет вообще.
- Тесты: ученик не видит чужих данных; родитель — только своих детей; изменение роли и вход попадают в аудит.
- Просмотр карточки ученика и выгрузка списка создают запись аудита доступа.
- Записи аудита и согласий невозможно изменить или удалить через API (проверяется тестом).
- Вход под созданным пользователем, смена пароля и выход работают в браузере.

## Этап 2. Учебный год, группы, ученики, справочники

**Состав**

- Учебные годы и периоды, переключение активного года.
- Группы, зачисление учеников (с датами), перевод между группами.
- Предметы, аудитории, категории оценок с весами.
- Назначения «преподаватель ↔ предмет ↔ группа» с периодом действия.
- Брендинг в БД применяется на экране входа и в шапке.
- Аудит всех изменений справочников.

**Критерии приёмки**

- Админ создаёт год, период, группу, учеников, предметы и назначения **без разработчика**.
- Учитель видит только свои назначения (проверено тестом API с его сессией).
- Удаление предмета, по которому есть оценки, запрещено с понятным сообщением.

## Этап 3. Расписание и уроки

**Состав**

- Шаблон расписания по группе (день, пара, время, предмет, учитель, аудитория), с датами действия.
- Исключения: отмена, перенос, замена на конкретную дату.
- Генерация уроков из шаблона на период; статусы урока.
- Замены преподавателя (`substitution`) с причиной.
- Просмотр расписания для группы, учителя, ученика, родителя.

**Критерии приёмки**

- У двух групп — независимые расписания, конфликтов нет.
- Перенос пары не ломает уже проведённые уроки и не перезаписывает чужие правки.
- Замена «на один урок» и «на две недели» работает; в отчёте видно фактического преподавателя.

## Этап 4. Журнал: оценки и посещаемость

**Состав**

- Экран урока: оценки (число, «+», «.»), категория, комментарий; посещаемость (П/О/У/Б/Н) с причиной.
- Массовые операции: отметить всех присутствующими, проставить оценку группе.
- Правила эскалации «плюсы/точки → оценка»: настройка, серверный расчёт, журнал срабатываний.
- Правка и мягкое удаление оценки с указанием причины; история правок в интерфейсе.
- Аналитика: средний балл (с весами) по ученику, группе, предмету, периоду; процент посещаемости.
- Выгрузка CSV/Excel и печать журнала.
- Приватность: ученик видит только свои оценки, родитель — только своих детей.

**Критерии приёмки**

- Оценка за урок ставится быстрее, чем в прототипе (замер: не более трёх действий на оценку).
- Плюсы и точки превращаются в оценку ровно один раз; повторный пересчёт ничего не меняет (тест).
- Есть тест: ученик через API не получает чужую оценку ни одним из способов.
- История правок показывает: кто, когда, что было и что стало.

## Этап 5. Домашние задания и вложения

**Состав**

- Публикация задания: текст, срок, вложения (ссылка, файл, картинка).
- Сдача решения учеником: текст + вложения; черновик и отправка.
- Проверка учителем: отзыв, оценка, при необходимости создание оценки в журнале.
- Хранилище за абстракцией: локальный диск по умолчанию, S3/WebDAV как опция; лимиты и проверка типов.
- Выдача файлов через API с проверкой прав.

**Критерии приёмки**

- Учитель и ученик прикрепляют файлы и ссылки; файлы не попадают внутрь контейнера, а лежат в настроенном хранилище.
- Ученик не может скачать чужую работу (тест).
- Смена хранилища на S3 не требует изменений в коде (проверяется на тестовом стенде).

## Этап 6. Эксплуатация: бэкапы, безопасность, наблюдаемость, установка

**Состав**

- `pg_dump` по расписанию, ротация, **шифрование архивов** ключом вне сервера, инструкция и **проверенное** восстановление.
- **Выгрузка и загрузка данных из админского интерфейса (предложение владельца, обсудить состав).**
  Идея: администратор скачивает из интерфейса снимок данных и умеет восстановить его обратно —
  например в JSON, без доступа к серверу и командной строке.
  Что важно решить до реализации:
  1. **Разделить две задачи.** Полный бэкап (вся база, `pg_dump`, шифрование, хранение вне сервера) —
     это восстановление после аварии; выгрузка «своих справочников и учебного года» в JSON — это
     прозрачность и перенос между стендами. Одно не заменяет другое: JSON не восстановит пароли,
     сессии, аудит и идентификаторы один в один.
  2. **Безопасность.** Выгрузка содержит персональные данные учеников и представителей, поэтому:
     доступ только `settings:write@all` (или отдельное право `backup:export`), обязательная запись в
     аудит (кто, когда, что выгрузил), предупреждение в интерфейсе, ограничение размера и срока
     жизни файла. Пароли и хеши, содержимое согласий и политик, сессии и аудит в выгрузку **не
     попадают**.
  3. **Восстановление сложнее выгрузки.** Импорт должен быть транзакционным, с проверкой версии
     схемы (снимок из другой версии — отказ с понятным сообщением), с двумя режимами:
     «добавить к существующим» и «заменить текущий год» (второй — только на пустой базе либо с
     подтверждением), с отчётом «создано / пропущено / конфликты».
  4. **Формат:** один файл JSON со схемой, версией приложения и версией миграций; человек читаемый,
     поэтому удобен для проверки и для подготовки тестовых наборов (см. также предложение о
     документе с моделью данных).
  5. **Что не обещать:** JSON-выгрузка не отменяет `pg_dump` и проверенного восстановления — в
     документации это должно звучать прямо, иначе появится ложное чувство защищённости.
  Скорее всего это отдельный шаг внутри Этапа 6 или сразу после него; объём зависит от ответов по
  пунктам 1–3.
- Срок хранения и уничтожение: команда `retention:purge`, отчёт и запись в аудите (ADR-022); обезличенный режим выгрузок.
- Процедура реагирования на инциденты: уведомление ответственного, страница событий безопасности, чек-лист действий (`SECURITY.md` §7).
- Структурированные логи с ротацией, `/api/health` и `/api/ready`.
- **Наблюдаемость бизнес-событий в логах:** единая схема сообщений (событие, сущность,
  идентификаторы, `requestId`), события генерации уроков, оформления и снятия замены, правок
  расписания и синхронизации каталога прав, `requestId` в теле ответа об ошибке, ротация и срок
  хранения логов. Правила ведения логов — в `DEVELOPMENT.md` §8, текущее состояние — там же
  отмечено как «есть/чего не хватает».
- Скрипты деплоя: обновление, переключение ветки, откат на предыдущую версию.
- Документация: установка на чистый сервер, обновление, восстановление, резервное копирование, порядок доступа.
- Мастер настройки и CLI-вариант (`npm run setup`).

**Критерии приёмки**

- Установка на чистую Ubuntu-машину по документации занимает менее часа и не требует правок кода.
- Восстановление из бэкапа выполнено и подтверждено на тестовом стенде.
- Архив бэкапа не читается без ключа (проверяется фактически).
- Выполнен прогон `retention:purge` на тестовых данных: отчёт сформирован, факт в аудите.
- Откат на предыдущую версию проверен.

## Этап 7. Ограниченный тест и подготовка к эксплуатации

**Состав**

- Тестовый стенд для 2–5 человек, фиксация замечаний.
- Разбор обратной связи, доработка интерфейса (в том числе упрощение навигации).
- Прогон сценариев на реальных данных ограниченного круга.
- Решение о выходе «в прод»: критерии — нет блокирующих дефектов, бэкап проверен, роли и приватность подтверждены тестами.

**Критерии приёмки**

- Все сценарии из `VISION.md` §3 пройдены на стенде живыми людьми.
- Пройден чек-лист оператора (`SECURITY.md` §8) в части, касающейся кода и данных: согласия зафиксированы, политика размещена, сроки хранения утверждены, восстановление проверено.
- Тесты приватности (ученик/родитель/учитель) зелёные на реальных данных стенда.
- Открытые дефекты классифицированы; блокирующих нет.

## Порядок и приоритеты

1. Этапы 0–2 — фундамент, без них всё остальное делается вслепую.
2. Этапы 3–4 — ядро ценности (журнал и посещаемость).
3. Этап 5 — домашние задания; можно параллелить с 4 после стабилизации прав.
4. Этапы 6–7 — перед допуском реальных людей.

**Состояние на сегодня**

- Этапы 0–3 приняты владельцем и в `main` (последнее слияние — PR #9, Этап 3).
- **Следующий шаг — Этап 4 «Журнал: оценки и посещаемость»** (`ROADMAP.md` §Этап 4). Опора уже
  есть: урок как единица журнала (ADR-006), категории оценок с весами, назначения, звонки и
  периоды, аудит, правило перевода ошибок БД в `409`.
- Баги по принятым этапам исправляются по ходу: отдельные правки в `main`, без ожидания
  следующего этапа. Каждая правка — с тестом и зелёными шлюзами.

**Идеи, отложенные по итогам Этапа 3** (полные формулировки и причины — `PHASE-3-FIXES.md`,
раздел «Подумать»):

- фильтровать преподавателей по назначению при постановке урока вручную;
- второй вид «Неделя» в «Сетке (шаблон)» с решением, куда девать кнопки правки;
- ограничить период пересоздания уроков периодами учебного года;
- темы оформления (шрифты, размеры, тёмный режим) — отдельный разговор;
- документ с актуальной моделью данных и фабрики тестовых данных;
- выгрузка и загрузка данных из админского интерфейса (Этап 6);
- наблюдаемость бизнес-событий в логах (Этап 6).

**Замечания владельца на будущее** (записано со слов, сроки и детали не обсуждались; в работу
берём только после отдельного разговора — не «между делом»):

- [ ] **Не запрашивать данные недоступных разделов (убрать 403 из консоли).** У ученика на
      каждый переход приходится по 8 ответов `403`: `/api/academic-years`, `/api/assignments`,
      `/api/groups`; у преподавателя — `/api/users`, `/api/roles`. Меню эти разделы не
      показывает, но маршруты **монтируются** при переходе, и экраны сразу идут за данными, на
      которые прав нет. Правильно: гейт на маршруте по тем же правам, что и в меню, и вместо
      монтирования — «нет доступа». Решение владельца: **ученику ни к чему знать, что есть
      что-то лишнее**, поэтому лишних запросов быть не должно вовсе. Проверка: под учеником и
      представителем на разрешённых экранах **ни одного 403**.
- [ ] **Фабрики тестовых данных.** Подготовка данных в интеграционных тестах — копипаста:
      «создай год, группу, предмет, преподавателя, назначение, шаблон, сгенерируй уроки» повторяется
      в каждом сценарии. Из 7 800 строк тестов 6 200 — интеграционные, и большая их часть это
      подготовка. Предложение: `createStudyGroup()`, `createTeacher()`, `createStudentWithAccount()`,
      `createLesson(date)`, `createAssignment()` в `test/helpers`. **Срок — после закрытия Этапа 4**:
      делать это в середине этапа значит переписывать тесты, которые ещё меняются. Правило бюджета
      «30 строк подготовки на проверку» — в `DEVELOPMENT.md` §5.
- [ ] **Зависимость e2e-сценариев от дня недели.** `phase-3-schedule` ищет занятие в сетке,
      которая по умолчанию показывает **текущую** неделю, а уроки создаются на будущие даты:
      совпадение случайно и пропадает, например, в воскресенье. Нужно переводить сетку на
      неделю занятия — но спокойно и с разбором, а не подбором стрелок: попытка починить это
      «по пути» сломала тест сильнее. Найдено при проверке стенда владельца.
- [ ] **Профиль пользователя.** Собрать в одном месте личное: текущий «Обзор», но
      **без формы смены пароля**, и страницу с персональными данными. Свои данные
      администратор правит сам, **кроме логина**; остальные роли — только просмотр. Форма смены
      пароля переезжает на страницу персональных данных. Открытый вопрос: что именно попадает в
      «Обзор» после того, как форма пароля уедет.
- [ ] **Страница приветствия.** Единая стартовая страница для всех ролей; правка — только у
      администратора, остальные смотрят. **Наполнение уточняется позже** — без него не начинаем,
      иначе получится пустой экран.
- [ ] **Совместить «Назначения» и «Замены».** Механика совмещения **обсуждается позже**:
      не решено, как разделять «кто должен вести» и «кто ведёт на этой неделе».
- [ ] **Совместить «Сетку (шаблон)» и «Уроки».** Детали **обсуждаются позже**. Частично
      пересекается с уже отложенным «вторым видом „Неделя“» в «Сетке (шаблон)»: возможно, это
      одна и та же работа, и решать их стоит вместе.

**Правила работы на каждом этапе**

- Сначала тесты на домен и права, потом интерфейс.
- Одна ветка — один этап (или его крупная часть), PR с описанием и скриншотами.
- Миграции БД только вперёд; откат — через новую миграцию.
- Любое изменение прав или приватности сопровождается тестом.
