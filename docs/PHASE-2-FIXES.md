# PHASE-2-FIXES — правки по замечаниям к Этапу 2

План правок по замечаниям владельца (после сдачи Шагов 1–8 Этапа 2).

Источник: разбор интерфейса на тестовом стенде 10.10.2026. Замечания касаются
удобства и полноты уже сделанных разделов, новой схемы они не требуют —
кроме отложенных пунктов (специальность в справочник, гейт по редакции
политики).

Правило работы: один блок — один коммит с тестами. Этап 2 считается сданным
после закрытия блоков A–H и чистого прогона мастера на пустой базе.

## Блок A. Единый учёт учеников (корень проблемы)

Подтверждено владельцем: **ученик первичен, учётная запись — его атрибут**;
учётная запись создаётся **по необходимости** (не обязательна при заведении).

- [x] Контракты: `studentSummarySchema.username`, `studentAccountRequestSchema`, `account` в создании ученика, `suggestUsernameResponseSchema`.
- [x] Домен: транслитерация и подбор логина (`packages/domain/src/username.ts`, 11 тестов).
- [x] API: `POST /api/students` принимает `account` и создаёт карточку и учётную запись в одной транзакции.
- [x] API: `POST /api/students/:id/account` — учётная запись ученику, созданному ранее.
- [x] API: `GET /api/users/suggest-username?fullName=…` — свободный логин по ФИО.
- [x] API: `GET /api/students` отдаёт `username` (состояние связи видно в списке).
- [x] Интерфейс: в «Пользователи и роли» блок «Новый ученик» (ФИО первым, дата рождения, примечание, чекбокс «создать учётную запись»).
- [x] Интерфейс: там же таблица «Ученики» с состоянием учётной записи и кнопкой «Создать учётную запись».
- [x] Интерфейс: из «Согласий и политики» убраны создание ученика и привязка представителя; раздел остался про политику, согласия и список учеников без согласия.
- A4 (связывание осиротевших карточек) — **отложено**: чистого прода нет, сделаем при переразвёртывании с нуля.
- Замечание по ходу: вставка пользователя при дубле логина давала `500` — Drizzle оборачивает ошибку БД, а перевод ошибок стоял не на всех вставках. Теперь `409` с текстом «Логин уже занят» (проверено тестом).

## Блок B. Группы и ученики

- [x] Порядок в карточке группы: зачисление → состав → отчисление по строке ученика.
- [x] Пустой список учеников объясняется текстом со ссылкой на раздел «Пользователи и роли».
- [x] Правка группы: форма «Править» (название, курс, специальность, границы периода). Учебный год не меняется — перенос означал бы другую группу.
- [x] Удаление группы кнопкой «Удалить», доступной только для пустой; для занятой сервер отдаёт `409` с `details.usedBy`.
- Тесты: 2 новых интеграционных (правка сохраняет год; пустая группа удаляется, занятая — нет). Замечание по ходу: новые тесты сначала стояли до зачисления, поэтому «занятая» группа была пустой — перенесены в конец, где состав уже создан.

## Блок C. Учебный год: периоды

- [x] Кнопки «Править» и «Удалить» в таблице периодов (правка — название и границы; тип периода не меняется).
- [x] API `DELETE /api/periods/:id` с записью в аудит: ответ `204`, повторное удаление — `404`.
- Замечание: проверка занятости периода появится вместе с правилами оценок и оценками (Этап 4) — тогда же сюда добавится `details.usedBy`, как у справочников. Сейчас на период ничего не ссылается, а внешний ключ с `on delete restrict` подстрахует на уровне базы.
- Тесты: 1 новый интеграционный (правка, удаление, повторное удаление).

## Блок D. Общая проверка дат

- [x] Одна проверка календарной даты на клиенте: `requiredISODateSchema` в `packages/contracts` (переиспользует `isISODate` из домена).
- [x] Применено к формам: год, период, группа, назначение (включая порядок дат).
- [x] Тесты: високосный день принимается, «31 февраля», «31 апреля», «13-й месяц» и пустое значение отвергаются.
- Замечание: в `<input type="date">` браузер обычно не даёт ввести несуществующую дату, но при ручном вводе пропускает — проверка закрывает и этот случай, и сообщение теперь понятное («Такой даты не существует»).
