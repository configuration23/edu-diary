План развития разделов «Расписание» и «Уроки» по итогам разбора концепции владельца
(модуль «Расписание, Уроки и Замены») и просмотра релиза Этапа 3.

Решения владельца зафиксированы ниже; спорные места отмечены как «не делаем» с причиной,
чтобы к ним не возвращаться. Схема БД в этих шагах **не меняется**: план — надстройка над
уже работающими слоями (`schedule_entry` — базовая сетка, `schedule_exception` /
`substitution` — оперативный слой, `lesson` — материализованные занятия).

## Состояние

**Этап принят владельцем: всё сделанное влито в `main`** (PR #9, коммит слияния `d954604`).
Заход A и шаги 0–2 сделаны, правки по трём просмотрам релиза внесены; журнал замечаний и список
отложенного — в `PHASE-3-FIXES.md`. Этот документ остаётся как история решений: что решили и
почему, чтобы не обсуждать закрытые вопросы заново.

## Что решено твёрдо

1. **Замены публикуются сразу.** Черновика и повторной публикации нет.
2. **Оформляет замены только администратор** (`substitutions:write@all`).
3. **«Быстрая замена» — от урока**, а не от отсутствующего преподавателя. Режим «кто
   отсутствует» — в возможные доработки.
4. **Дневное расписание делаем**, с переключением «один день / вся неделя».
5. **Дневной вид как отдельный экран с мобильным режимом — Этап 6**, но API и контракты
   закладываются уже сейчас (шаг 0), чтобы Этап 6 не переделывал модель.
6. **Тип пары** (лекция/практика/лабораторная) — в возможные доработки: поле `lesson_type`
   в базе и `lessonType` в контракте уже есть, но заполнять его нечем без учебного плана.
7. **Уведомления** — только визуальные в интерфейсе. Чекбокса «оповестить» не делаем
   вообще, пока нет канала: неработающий чекбокс хуже его отсутствия.
8. **Порядок работ**: сначала мелкие правки из `PHASE-3-FIXES.md`, затем шаг 0, шаг 1,
   шаг 2.

## Заход A. Мелкие правки (из `PHASE-3-FIXES.md`)

Закрывается одним заходом до новой функциональности, потому что переименование раздела и
порядок блоков затрагивают те же экраны, что и шаги 1–2, — делаем один раз.

- [ ] «Начало» в назначениях — по умолчанию начало активного учебного года, поле редактируемо.
- [ ] Группа «Все» в назначениях: назначение по предмету во все группы выбранного года.
- [ ] «Действует с» в блоке «Добавить занятие» — по умолчанию начало учебного года.
- [ ] «Пользователи и роли» → «Учётные записи и роли» (навигация, тексты раздела,
      перекрёстные ссылки, сквозные проверки).
- [ ] В «Расписании» блок добавления занятия — первым и всегда видимым (см. шаг 1).
- [ ] Название аудитории серым текстом в списках выбора.

## Шаг 0. Фундамент: данные под дневной вид и безопасная замена — **готово**

- [x] **0.1. Проверка занятости заменяющего — дефект.** Сейчас занятость проверяется у базовой
  сетки, а у `createSubstitution` — нет: одного преподавателя можно назначить на две пары
  в одно время. Добавляем проверку рядом с `assertSlotFree`, ответ `409` с
  `details.reason = 'substitute_overlap'`.
- [x] **0.2. `GET /api/lessons/:id/substitute-candidates`** — активные преподаватели со статусом
  на слот: `free` / `busy` (с группой, предметом и парой) / `assigned`. Сначала свободные.
  Право `substitutions:write`.
- [x] **0.3. `substitutionId` в `LessonDto`** — карточка урока ссылается на запись замены и её
  причину. Поле additive, схему не трогает.
- [x] **0.4. Признак «есть замены» на дату** отдельным API не заводим: выводится из уроков
  (`status = replaced` или `substitutionId != null`). Решение фиксируем, чтобы в Этапе 6
  не изобретать поле.
- [x] **0.5. Заготовок-обманок нет**: никакого чекбокса уведомлений, никаких пустых полей.

**Проверено:** 318 тестов (в том числе занятый заменяющий → `409`, кандидаты во всех
трёх статусах, `substitutionId` в уроке), 12 сквозных сценариев, архитектура, типы, формат и
сборка — зелёные.

## Шаг 1. Экран «Расписание» — день и неделя — **готово**

- [x] **1.1. Разделение терминов**: текущий шаблон → **«Сетка (шаблон)»**; новый экран →
  **«Расписание»** (день/неделя). Иначе ученик ищет своё расписание там, где админ ставит
  шаблон.
- [x] **1.2. Один экран, два вида**, вид в URL: `/schedule?date=…&view=day|week`. Ссылку можно
  отправить, «сегодня» не сбрасывается.
- [x] **1.3. Вид «День»**: дата-стрип с бейджем «есть замены»; таймлайн пар по звонкам (пустой
  слот — «окно»); линия текущего времени и метка «идёт сейчас»; карточка урока с предметом,
  преподавателем, аудиторией, темой и статусами (🟢 по плану, 🟡 замена с блоком
  «Вместо: … → Назначен: …», 🔴 отмена, 🔵 перенос). Админу — действия в карточке.
- [x] **1.4. Вид «Неделя»**: матрица Пн–Сб × пары, компактные ячейки, пустые — «окно», клик по
  ячейке открывает карточку. Drag-and-drop не делаем.
- [x] **1.5. Группа выбирается в блоке добавления занятия** (вверху страницы), список занятий
  подгружается по ней; «Все доступные группы» — все занятия. Селект группы из шапки на этих
  экранах убираем, чтобы не было двух разных «Группа» на одной странице.
- [x] **1.6. Правка занятия и урока — управляемый редактор**: получает строку из списка,
  закрывается кнопкой «Закрыть» (и Escape), а не «само» после сохранения.

**Проверено:** сквозной сценарий (админ ведёт сетку, преподаватель и ученик видят расписание,
виды «день/неделя» переключаются), интеграционные тесты выборки по правам, все шлюзы зелёные.
Виды живут на одном экране, вид не сбрасывается при переключении дня; окно запроса — три недели
вокруг выбранной даты, поэтому переключение вида не ходит на сервер повторно.

## Шаг 2. Быстрая замена и журнал замен — **готово (на экране «Замены»)**

- [x] **2.1. Виджет «Быстрая замена»**: выбор даты и урока (или кнопка «Заменить» в карточке
  дня); исходный урок read-only; **кандидаты со статусами** из 0.2; причина (больничный,
  командировка, мероприятие, другое); при необходимости новая аудитория с проверкой
  занятости. Сохранение — сразу опубликовано.
- [x] **2.2. Журнал замен**: таблица активных замен за период (дата и пара, кто заменён, кто
  ведёт, причина, кто оформил), фильтры по группе, преподавателю и дате. Опирается на
  существующий `GET /api/substitutions`.
- [x] **2.3. Чтение для всех ролей**: заменяющий видит чужой урок в своём дне; ученик и родитель
  видят замену на карточке урока (уже работает и покрыто тестом).

**Как сделано.** Раздел «Замены»: блок «Быстрая замена» (урок → кандидат со статусом →
причина; «Другое» с текстом) и журнал действующих замен с кнопкой «Снять». Черновика нет:`nзамена публикуется сразу.

**Проверено:** 318 тестов (в том числе занятый заменяющий → `409`), 12 сквозных сценариев,
архитектура (132 файла), типы, формат и сборка зелёные.

## Отменённые уроки: не мусорить и не попадать в тупик

Сейчас «Отменить занятие» ставит урок в `cancelled`, и вернуть его из интерфейса нельзя —
только снять исключение через API. Закрываем цикл:

- фильтр по статусу в списке уроков, **отменённые скрыты по умолчанию** (переключатель
  «показать отменённые»);
- **кнопка «Восстановить»** на отменённом уроке: снимает исключение и возвращает пару в план;
- **удаление остаётся аварийным инструментом администратора** (дубли, тестовые данные), но
  не основным путём: оно не убирает исключение, и на дату с отменой урок появится снова.

## Что не делаем и почему

| Пункт | Решение |
|---|---|
| Drag-and-drop в матрице | Дорого и конфликтует с моделью «шаблон + исключения + уроки»; клик по ячейке даёт ту же пользу |
| Черновик и повторная публикация замен | Решение владельца: публикуется сразу |
| Объединение групп, перенос предмета как тип замены | Требует расширения модели: несколько групп на один урок |
| Чередование недель (числитель/знаменатель) | До реального учебного плана это была бы догадка |
| Тип пары в интерфейсе | Поле и контракт есть, заполнять нечем — в возможные доработки |
| Внешние уведомления и чекбокс «оповестить» | Нет канала; визуальные пометки делаем |
| Мобильные жесты, bottom sheet | Сначала нормальное чтение экрана на телефоне (Этап 6) |
| Отдельный экран «Моя нагрузка» | Не нужен: тот же дневной вид с фильтром по правам преподавателя |
| Режим «кто отсутствует» в быстрой замене | В возможные доработки (решение владельца: начинаем от урока) |

## Возможные доработки (на будущее)

- тип пары: лекция, практика, лабораторная (поле есть);
- быстрая замена «от отсутствующего преподавателя»: «кто заболел» → все его пары на дату;
- чередование недель, если появится учебный план;
- черновик замен и история правок, если понадобится контроль публикации;
- объединение групп и перенос предмета на другую пару;
- уведомления (почта/мессенджер) — вместе с появлением канала;
- мобильный режим дневного расписания: лента дней, жесты, bottom sheet.

## Связь с другими этапами

- **Этап 4** (оценки и посещаемость) опирается на урок: тип пары и дневной вид сюда не
  входят, но не мешают.
- **Этап 6**: мобильный режим дневного расписания и уведомления. API и контракты под них
  заложены в шаге 0.
