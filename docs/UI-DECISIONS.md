# Решения по оформлению интерфейса

**Все девять решений приняты владельцем.** Числа «сколько вариантов сейчас» — из
[`UI-INVENTORY.md`](./UI-INVENTORY.md) (`npm run ui:inventory`).

## Правило, по которому решаем

> **Одинаковый смысл — одинаковое оформление. Разный смысл — намеренно разное.**

Без правила любое расхождение можно назвать особенностью. С правилом решение проверяемо — и его
можно записать так, чтобы `check:ui` это проверял.

## Принятые решения

| № | Решение | Что делаем |
|---|---|---|
| 1 | Размещение создания | Три варианта по смыслу: кнопка в шапке списка; внутри объекта (период года, зачисление в группу); постоянной отдельной карточки **не остаётся** — `UsersScreen` привести к общему виду |
| 2 | Главный цвет | Один акцент для действий. `slate-900` из действий убрать, навигация — подсветкой. `sky` остаётся **выделением** (день, ячейка), а не вторым акцентом |
| 3 | Переключатели вида | Отдельный примитив **«сегмент»**, не кнопка и не ссылка: своя высота и своё состояние «выбрано» |
| 4 | Ссылки | Один примитив `Link` + отдельный вид для навигации |
| 5 | Размеры кнопок | **Два**: обычный и мелкий (строки таблиц) |
| 6 | Контролы | Примитивы `TextInput`, `Select`, `Textarea`, `Checkbox`, файл. Высота, рамка, радиус — внутри примитива; в экранах этих классов нет |
| 7 | Отступы | Шкала из трёх: `gap-1` внутри элемента, `gap-3` между полями, `gap-6` между блоками. `gap-2`, `gap-4`, `gap-5` из контейнеров убрать |
| 8 | Вложенность | Не больше **двух рамок** по пути к содержимому. Спойлер — контейнер, не рамка |
| 9 | Заголовки | `h1` — страница, `h2` — блок, `h3` — подблок; уровень соответствует вложенности |

## Палитра

Основа — проверенные шкалы Tailwind: **`slate`** как нейтраль, **`blue`** как единственный акцент,
**`emerald` / `amber` / `red`** как смысловые цвета. Не «подбор на вкус»: у этих шкал ровные шаги
светлоты, поэтому светлая и тёмная темы собираются из одних и тех же ступеней.

Имена — **по роли**, и утилиты читаются как класс: `bg-card`, `text-muted-foreground`,
`border-input`, `bg-primary`. Экран не знает, что акцент синий.

### Оговорка про рамки полей — сознательное отступление

Для **элементов управления** норма другая — 3:1. Замеры:

| Рамка | На белой карточке |
|---|---|
| `#e2e8f0` (как сейчас в разметке) | **1.23:1** |
| `#cbd5e1` (`slate-300`, сейчас в полях) | **1.48:1** |
| `#94a3b8` (`slate-400`, предлагаю) | **2.56:1** |
| `#64748b` (`slate-500`) | 4.76:1 |

Строгую норму проходит только `#64748b`, но в плотной форме на 80 контролов такая рамка начинает
доминировать над содержимым.

**Решение:** поле получает `#94a3b8` — заметно темнее нынешнего (1.48 → 2.56) — и опирается не только
на рамку: у поля всегда есть подпись, фон `surface-sunken` и кольцо фокуса (6.70:1). Это **одна
переменная**: если понадобится строгое соответствие (например, требование закупки), меняем
`--color-input` на `#64748b` — и весь интерфейс соответствует норме без переделки.

## Цвет предмета и темы

Цвет предмета приходит **из базы** (`#rrggbb`) и **остаётся частью дизайна**: он означает предмет —
это данные с оформлением, а не случайный оттенок. Решение владельца, зафиксировано явно.

Поэтому цвет предмета применяется там, где он и был задуман:

| Что | Как |
|---|---|
| Метка, точка предмета | цветом предмета — как есть |
| Заливка плитки урока | цветом предмета — как есть |
| Текст интерфейса | ролями темы: цвет предмета не заменяет основной текст |

Последняя строка — **не ограничение, а граница**: в текущем коде названия предметов уже выводятся
основным цветом текста, а цветная только метка. Так и остаётся — менять нечего.

**Улучшение для тёмной темы, без изменения данных:** заливку плитки лучше считать через
`color-mix(in oklab, <цвет> 12%, var(--color-card))` вместо `${color}22`. Сейчас к hex приклеивается
прозрачность, и на тёмном фоне такая заливка почти не видна. `color-mix` подмешивает цвет к
**фоновому токену**, поэтому плитка читается в обеих темах, а цвет предмета остаётся прежним.

## Фундамент тем

Сейчас `dark:` не используется **ни разу**, а `body` жёстко задан как `bg-slate-50 text-slate-900`.
Фундамент — это три вещи, и его дешевле заложить до раскатки, чем переделывать 24 экрана дважды.

**1. Один набор семантических токенов.** Имена — по роли, не по оттенку: `surface`, `surface-raised`,
`text-muted`, `accent`, `danger`. В компонентах и экранах **нет** `slate-500`, `blue-700` — только
роли. Тогда тема — это подмена значений, а не переписывание классов.

**2. Переключение атрибутом.** Светлые значения — по умолчанию в `@theme`; тёмные — в
`:root[data-theme='dark']`. Системная настройка — через `prefers-color-scheme`, когда атрибута нет.
Для редких мест — `@custom-variant dark`.

**3. Экран не выбирает цвет.** Ни один экран не должен знать, что акцент синий. Если появится
фирменный цвет заведения — меняется одна переменная, а не 24 файла.

**Хранение выбора** (светлая / тёмная / как в системе) — отдельный шаг: `localStorage` сейчас,
серверная настройка позже. Фундамент от этого не зависит.

## Что не меняем

| Что | Почему |
|---|---|
| Цвет предмета (из базы) | **Часть дизайна**: цвет несёт смысл предмета и остаётся как есть |
| Цвета статусов | Успех / предупреждение / ошибка / ожидание — разный смысл |
| «Опасное» действие отдельным тоном | Удаление и отчисление должны отличаться от обычного действия |
| Спойлеры свёрнутыми по умолчанию | Решение владельца по страницам |
| Создание внутри объекта | Период принадлежит году, зачисление — группе |

## Порядок работ

1. **Токены** — значения из таблиц выше в `index.css`: светлые в `@theme`, тёмные в
   `[data-theme='dark']`. Плюс шкала отступов, радиусы, высоты контролов. **Фундамент тем — здесь.**
2. **Примитивы** — `Select`, `Textarea`, `Checkbox`, `Link`, `Segmented`, `Stack`, `FormActions`.
   Проверка на двух экранах, скриншоты «до/после», проверка в обеих темах.
3. **Раскатка** — по 3–4 экрана на ветку; в каждой ветке замена палитры на роли.
4. **Замок** — `check:ui`: в `screens/` запрещены сырые `<select>`, `<textarea>`, класс рамки,
   `bg-slate-900` на действиях и **любые** `slate-*` / `blue-*` / `emerald-*` вместо ролей.
5. **Документ** — `docs/UI-KIT.md`: классы объектов и правило выбора.

## Проверка результата

503 теста и 18 сквозных сценариев **внешний вид не проверяют** — «поехавшая вёрстка» пройдёт мимо.
Поэтому: Playwright снимает каждый экран под каждой ролью при фиксированном размере окна, **в двух
темах**; снимки «до» становятся эталоном.
