# Решения по оформлению интерфейса

Документ для **согласования**, а не отчёт. По нему принимается, что привести к одному виду, а что
оставить разным. Числа взяты из [`UI-INVENTORY.md`](./UI-INVENTORY.md) (`npm run ui:inventory`).

## Правило, по которому решаем

> **Одинаковый смысл — одинаковое оформление. Разный смысл — намеренно разное.**

Без правила спор бесконечен: любое расхождение можно назвать «особенностью». С правилом решение
проверяемо — и его можно записать так, чтобы `check:ui` это проверял.

## Решение 1. Размещение создания

**Сейчас:** четыре варианта.

| Вариант | Где |
|---|---|
| Кнопка в шапке списка, форма над списком | год, группа, ученик, назначение, предметы, аудитории, причины, звонки, шаблон недели, замены |
| Постоянная отдельная карточка | `UsersScreen` — «Новый пользователь» |
| Внутри объекта | «Добавить период» в карточке года, «Зачислить» в составе группы |
| Отдельная секция-спойлер | «Страница «Обзор»» в настройках |

**Предлагаю:** три варианта, по смыслу.

1. **Создание в разделе** — кнопка в шапке списка, форма раскрывается над списком. Это уже
   принятый порядок.
2. **Создание внутри объекта** — остаётся внутри панели объекта. Период принадлежит году, зачисление
   — группе: вынести их в шапку значит потерять, к чему они относятся.
3. **Постоянной отдельной карточки не остаётся.** `UsersScreen` привести к варианту 1.

## Решение 2. Главный цвет

**Сейчас:** два акцента, оба претендуют на «главный».

| Токен | Раз | Где |
|---|---|---|
| `bg-blue-700` | 1 | только `ui.tsx` — кнопка `primary` (**правильно**) |
| `bg-slate-900` | 6, в 3 файлах | навигация, переключатели вида, плашка оценки (**по месту**) |
| `bg-sky-*` | 18 | выделение дня и выбранной ячейки в уроках и журнале |

**Предлагаю:** один акцент для действий — синий. `slate-900` из **действий** убрать; навигацию
оставить подсветкой без «чёрной плашки». `sky` оставить как **выделение** (день, ячейка) — это другое
значение, и оно не конкурирует с кнопкой.

## Решение 8. Вложенность блоков

## Что я предлагаю **не** менять

Перечисляю явно, чтобы это не всплыло потом как «забыли»:

| Что | Почему оставить |
|---|---|
| Цвет предмета (из базы) | Это **данные**, а не оформление: цвет несёт смысл предмета в расписании |
| Цвета статусов (`Badge`, `Alert`) | Успех / предупреждение / ошибка / ожидание — разный смысл |
| «Опасное» действие отдельным тоном (`danger`) | Удаление и отчисление должны отличаться от обычного действия |
| Спойлеры свёрнутыми по умолчанию | Решение владельца по страницам |
| Создание внутри объекта | Период принадлежит году, зачисление — группе (решение 1) |

## Порядок работ после согласования

1. **Токены** — цвета, радиус, шкала отступов, высоты контролов в одном месте.
2. **Примитивы** — недостающие `Select`, `Textarea`, `Checkbox`, `Link`, `Segmented`, `Stack`,
   `FormActions`. Проверка на двух экранах со скриншотами «до/после».
3. **Раскатка** — по 3–4 экрана на ветку.
4. **Замок** — `check:ui`: запрещает в `screens/` сырые `<select>`, `<textarea>`, класс рамки и
   `bg-slate-900` на действиях. Без замка через полгода всё вернётся.
5. **Документ** — `docs/UI-KIT.md`: классы объектов и правило выбора.

## Проверка результата

Существующие 503 теста и 18 сквозных сценариев **внешний вид не проверяют** — «поехавшая вёрстка»
пройдёт мимо. Поэтому нужен визуальный контроль: Playwright снимает каждый экран под каждой ролью
при фиксированном размере окна, снимки «до» становятся эталоном.
