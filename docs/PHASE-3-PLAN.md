# План Этапа 3 — расписание и уроки

Опирается на `ROADMAP.md` (Этап 3), `ARCHITECTURE.md` §5 и ADR-006…009. Цель этапа: админ
составляет расписание группы, система порождает уроки, а замены и переносы сохраняют историю
«кто вёл» и «что было».

## 1. Что должно получиться

1. **Шаблон расписания группы**: «вторник, 2-я пара, 9:00–10:30, Основы программирования,
   ДЕМО-кабинет 101, действует с 1 сентября по 31 декабря».
2. **Исключения на конкретную дату**: отмена, перенос (время/аудитория), замена преподавателя.
3. **Уроки**: конкретные занятия на дату, порождённые из шаблона; у урока свой статус, тема и
   аудитория. Оценки и посещаемость Этапа 4 будут ссылаться именно на урок (ADR-006).
4. **Замены преподавателя**: на один урок или на диапазон дат, с причиной; в уроке видно, кто
   фактически ведёт.
5. **Просмотр расписания** для группы, преподавателя, ученика и законного представителя — с
   учётом прав и приватности: ученик видит расписание своих групп, представитель — расписание
   групп своих детей, преподаватель — свои занятия.

## 2. Ключевые решения

- **Шаблон ссылается на назначение.** `teaching_assignment` уже описывает «кто, что, в какой
  группе и в какой период». Шаблон добавляет «в какой день недели и какой парой». Это убирает
  дублирование: предмет, группа и преподаватель берутся из назначения, а не вводятся заново.
- **Урок — материализация шаблона на дату.** Генерация на период создаёт строки уроков
  (идемпотентно: повторный запуск не дублирует и **не перезаписывает** правки). Урок можно
  отменить, перенести, задать тему — шаблон при этом не меняется.
- **`unique (study_group_id, lesson_date, pair_number)`** (ADR-006): в одной группе не может быть
  двух уроков на одной паре — это и есть «конфликтов нет» из критериев приёмки.
- **Замена — отдельная сущность** (ADR-009): ссылается на назначение, опционально на урок, и/или
  на диапазон дат, содержит заменяющего и причину. Урок получает статус `replaced` и фактического
  преподавателя, история сохраняется.
- **Время пары хранится в шаблоне** (`time_start`, `time_end`), а не выводится из номера пары:
  сетка звонков различается между заведениями, а зашитая в код сетка стала бы догадкой.
- **Наложение проверяется здесь.** `ADR-030` отложил проверку «две пары в одно время» до
  расписания: теперь у нас есть день недели, номер пары и время, поэтому правила становятся
  проверяемыми: преподаватель не может вести две группы в одну пару, аудитория не может быть занята
  дважды. Это и закрывает долг того решения.

## 4. Определение готовности (из `ROADMAP.md`)

1. У двух групп — независимые расписания, конфликтов нет (нет двух уроков на одной паре в группе,
   нет преподавателя в двух местах в одно время, нет двух занятий в одной аудитории).
2. Перенос пары не ломает уже проведённые уроки и не перезаписывает чужие правки.
3. Замена «на один урок» и «на две недели» работает; в отчёте видно фактического преподавателя.
4. Плюс общие правила проекта: `npm test` (включая интеграционные с `TEST_DATABASE_URL`),
   `npm run typecheck`, `npm run format:check`, `npm run check:architecture`, `npm run build`,
   зелёный CI и сквозные сценарии.

## 5. Открытые вопросы к владельцу

1. **Сетка звонков**: время пары задаётся вручную при создании шаблона или заводится справочник
   «звонки» (номер пары → время) на уровне заведения? Пока: вручную, с подсказкой типового времени.
2. **Кто может править расписание**: только администратор (`schedule:write@all`) или ещё и
   заведующий отделением (роль появится позже)? Пока: администратор.
3. **Замены**: должен ли заменяющий видеть чужой урок в своём расписании сразу после назначения
   замены? Пока: да, видит — иначе замена бессмысленна.
